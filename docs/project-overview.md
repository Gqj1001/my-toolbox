## 三、网站的公共设施（跟具体工具无关的部分）

### 1. 登录
用 **Supabase 的邮箱 + 密码**（有注册页、登录页、邮箱确认链接）；**没有**微信/QQ 等第三方登录。
没登录的人**什么页面都进不去**（连工具本身的网页文件也拦），送去登录页；登录后自动回到原来想去的页面。

### 2. 会员系统
**「免费 / 会员 / 封禁」不是三个并列等级，而是两条轴**（这点最容易看错）：

| 轴 | 取值 | 存在哪 |
|---|---|---|
| 会员等级 | `免费版`（free） / `会员版`（vip） | `user_roles` 表的 `plan` |
| 账号状态 | `正常`（active） / `已封禁`（banned） | `user_roles` 表的 `status` |
| 到期时间 | 日期 | `user_roles` 表的 `expires_at` |

- **算不算有效会员** = 等级是会员 **且** 状态正常 **且** 到期时间还没过。三条缺一条就不是。
- **封禁**：状态改成「已封禁」后，整个网站都进不去，一律跳到 `/banned` 提示页。
- **开通方式**：**没有在线支付**。非会员点会员工具 → 跳到 `/upgrade` 页面 → 提示「联系管理员开通」。
  真正开通是管理员在后台点按钮。
- 没在 `user_roles` 里建过行的人，**一律当免费用户**处理。

### 3. 管理后台 `/admin`（只有管理员能进）

| 页面 | 能干什么 |
|---|---|
| `/admin` | **用户与权限管理**：列出所有用户，显示共几位管理员 / 有效会员 / 已封禁；给某人**开通会员**、**取消会员**、**封禁/解封**，改完立即生效 |
| `/admin/feedback-keywords` | 维护课后反馈的**关键词库**（按 学段 → 科目 → 教材 → 章节 级联选择，可编辑/归档关键词） |
| `/admin/feedback-candidates` | 审核 AI 批量导入的**关键词候选**，可通过/驳回，可导出 |

- 管理员权限读的是 `user_roles` 表的 `role`（只有 `admin` / `user` 两种）。
- **安全底线**：页面上藏起按钮不算保护——所有管理操作在服务器端**再验一次**身份才会执行。
- 还有一个**应急名单**（环境变量 `ADMIN_EMAILS`）：万一后台进不去，用它先把自己弄进去，之后仍以数据库为准。

### 4. 权限判断逻辑（一个工具能不能打开）

```
用户打开 /tools/某工具
  → 没登录？          → 送去登录页
  → 状态是已封禁？     → 送去 /banned
  → tools 表里查这条工具（只看 active = true 的）
      · 查不到        → 显示"页面不存在"
      · min_plan=vip 且用户不是有效会员 → 送去 /upgrade（提示开通）
      · 其余          → 打开
  → 打开时再看 public/tools/ 有没有对应网页：有就嵌进来，没有显示"功能开发中"
```

- **`tools` 表的 `min_plan`** 决定这个工具是免费还是会员专属；**`active`** 控制是否出现在目录里（`false` 等于下线）。
- **页内 AI 功能是单独再判一次**的：工具本身免费，但里面的 AI 润色/建议需要会员（三个工具都是这个口径）；
  `/admin/*` 另有一道守卫，必须是管理员。

> 💡 **想改「谁能用某个工具」**：改 `tools` 表的 `min_plan` 就行，不用改代码。
> 但**改完要去 Supabase 后台执行**（写进仓库的 SQL 不会自动生效）。

### ⚠️ 三个隐患（不是"现在坏了"，而是"以后会咬人"）

1. **`tools` 表的建表语句不在仓库里**（只有种子数据和权限设置）→ 照仓库脚本**重建不出**这张表，得从线上导出结构。
2. **会员那三列（`plan` / `status` / `expires_at`）的加列语句也不在仓库里** → 同上；
   而且新人容易误以为"跑一遍 migrations 就有会员功能"——**不会**。
3. **换工具权限没有后台界面** → 管理员后台**改不了** `tools` 表，只能去 Supabase 后台手工跑 SQL（容易忘、容易改错）。

## 五、两个 DSH 会话的分工

这个项目**同时开两个 DSH 会话**，各管一块，**互不越界**：

| 会话 | 管什么 | 主要动的文件 |
|---|---|---|
| **工具会话** | 工具**本身**（工具怎么算、怎么导 Word、AI 怎么写） | `public/tools/` 下的东西、`src/app/api/**` 的 AI 接口 |
| **网站会话** | 登录、会员、路由、目录、权限、后台 | `src/app/` 页面、`src/lib/`、`src/components/`、`supabase/migrations/` |

**两条约定**：① **不跨会话改对方的文件**——需要对方改就写清楚需求交过去，别自己动手；
② **不确定归谁时先问用户**，不要猜。理由：两边改的是同一批功能的两个层面（工具"算得对不对"
vs 网站"谁能进得来"），混着改容易一边修好另一边弄坏。所以 `public/tools/*.html` 是**工具本体**
（工具会话地盘），网站会话改的是**嵌它的那层壳**。


## 六、用户自己能做什么（不用找 DSH）

- 在 **Vercel** 看部署有没有成功（Deployments）；在 **Supabase 的 SQL Editor** 里跑 SQL（DSH 会给逐字命令）
- 在网站 **`/admin`** 给用户开会员、封禁、维护关键词
- 在 **Word** 里打开导出的 docx，检查格式；或给 DSH 发截图、报错信息

**用户不做**：读代码、改代码、看日志、用命令行（除非 DSH 给了可逐字复制的命令）。

> **安全**：DSH **绝不会**向你索要 `service_role` key、Vercel token、DeepSeek API Key —— 这些你自己在平台后台填。

## 八、页面性能

`/dashboard`、`/tools` 曾经慢 + 白屏：一次渲染要等好几次数据库往返，`SiteHeader` 还把页面刚查过的
会员/角色**又查了一遍**，且没有 `loading.tsx`。**第一批已修**（`getViewer()` 合并查询 + `React.cache()`
请求内去重 + 工具目录并发 + 两张骨架屏），实测往返 `6→5`、TTFB `681→291ms`。
**第二批已修**：`tools` 表加 30 秒进程内缓存（连着两次请求，第二次不再查库）。**还剩**导航预取
（`<Link>` 每次多带 **11 条**后台预取）——属取舍，暂不做。
⚠️ 管理员在 Supabase 改 `tools` 表后，**最多 30 秒**全站生效。详见 **`docs/perf-notes.md`**。

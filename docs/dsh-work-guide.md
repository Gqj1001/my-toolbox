# 跟用户配合的方式（每个新会话必读）

## 用户是谁
高中数学老师，**不懂代码**。所有代码操作交给 DSH。

## 沟通方式
- **大白话**，不要甩术语（"debounce"、"SSR"这种词要解释）
- 每做一步，说清：做什么、看到什么、不对怎么办
- 不要假设用户懂 git / 命令行 / Supabase 细节

## 工作节奏
1. **改代码前先给方案**，用户确认后再动手
2. **关键决策给选项**（A/B/C），不要自己拍板
3. **每步做完给结果**，用户确认后再进下一步
4. **不要一口气改太多**——真实 bug 和可选优化分两批

## 代码改动原则
- 每个真实 bug 修完，**加测试防护**（用户很在意"测试能不能真抓到 bug"）
- 提交前**跑全套回归**
- commit message 用户会看过再说
- **push 前停下**，用户去 Vercel 部署

## 安全边界
- **绝不要向用户索要**：service_role key、Vercel token、DeepSeek API Key
- 这些用户自己在平台后台填
- 测试账号：`roleb`=VIP、`rolea`=免费

## ⚠️ 这个项目里踩过的坑（新会话务必先看，能省几小时）

### 1. 测试断言「硬编码某个数字」→ 迟早假红

实测踩过好几次：`=== 11`（出网次数）、`=== 1`（热请求）、
「响应里必须有某句话」（措辞后来变过）、「首次访问没走缓存」（依赖缓存是否恰好为空）。
**一条优化上线后，这些数字会合法地变化，测试就红了，而产品是好的。**
写断言时优先用**口径**（「没有变多」「不是本机版」「已进入云端态」），
必须写数字时留**区间**并注明为什么。

### 2. 仓库里**已经有一份**东西时，先找它，不要另写一份

`parseDisplayDate`（日期解析）、`historyByStudent`（历史装配）、
`studentsByName`（学生装配）、`debug-gate`（调试开关）、`ttl-cache`（缓存）
—— 这些都已经存在且被复用。**第二个来源**是这个项目反复踩过的坑
（注释里甚至专门写了「这个项目已经在『标签有两个来源』上踩过一次」）。

### 3. Next.js 的两个静默陷阱（都实测过）

- **`process.env.NODE_ENV` 会在构建期被内联成常量**。
  于是「在运行期设 `NODE_ENV=test` 来绕开生产判断」**根本无效**，
  而且那种判断失败方向是「关闭」→ 你会得到一个永远不生效的开关。
  **要用就用自己的环境变量**（如 `ALLOW_DEBUG_CACHE_CLEAR`）。
- **`.select()` 必须是单字面量字符串**。写成 `"a" + "b"` 拼接会让 PostgREST
  的类型推断退化成 `GenericStringError`，**编译期**报 TS2352。

### 4. Supabase 的几个真实行为（不是猜的）

- **`reuse interval` 内复用同一个 refresh token 会被判「泄露」→ 撤销整个会话**。
  症状就是用户说的「每次进网站都要登录」，而且看起来**随机** ——
  只在「access token 剩 < 90 秒」这个窗口里恰好有并发请求时才发生。
  ⚠️ **光把它调大不能根治**：要减少**并发刷新**本身（见下一条）。
- ⚠️ **`auth.getUser()` 自己会刷新，而且带重试**（2026-10 收口 A-2 时实测，最费时间的一条）：
  `GoTrueClient.__loadSession()` 在 `expires_at - now < 90 秒` 时会调 `_callRefreshToken()`，
  而 `_refreshAccessToken()` 内部**还带指数退避重试**（200/400/800…ms）。
  **`auth: { autoRefreshToken: false }` 挡不住它**（那个开关只管后台定时器）。
  后果：一个请求里的一次 `getUser()` 能放大成 **18–24 次** `/auth/v1/token`。
  **要校验会话就别用 `getUser()`，直接打 `/auth/v1/user` 带 Bearer**（实测 1 次 vs 18 次）；
  **要刷新就自己打 `/auth/v1/token`**（不重试），并且**让 auth-js 读不到快过期的会话**
  （把 cookie 的读取过滤一层，见 `src/lib/session-freshness.ts` 的
  `hideStaleSessionFromAuthJs`）。
  ⚠️ 但**只能过滤「读」，不能动「写」（`setAll`）** —— 登录/登出都靠它写会话，
  去掉会让**登录直接失效**（本轮踩过，两个套件立刻变红）。
- **auth-js 的去重是「实例级」的**：`refreshingDeferred` 和 `_acquireLock` 都挂在
  客户端对象上。服务端每请求新建 client ⇒ **跨请求零去重**。
  所以「并发 N 个请求 → N 次刷新」是默认行为，必须有**进程内单飞**才挡得住。
- ⚠️ **`perf-notes.md` 六之三曾说「中间件跑在 Edge，与页面侧内存不共享」——这句是错的**。
  2026-10 实测（Next 16.3.8）：中间件往 `globalThis` 写的东西，页面侧的 API 路由**读得到**，
  且 `EdgeRuntime` 未定义 ⇒ 实际是 **Node 运行时、同一个进程**。
  所以「两边共用一份缓存」是可行的（A-2 收口就是靠它）。
  ⚠️ 但**别把结论建立在内存共享上**：写代码时让「共享内存」只是**优化**，
  拿不到就自动退化成各查一次（`readAuthUser` 返回 `undefined` 就是这个语义）。
- **cookie 里的会话有「两种形状」**：正式的是 `base64-<base64url(JSON)>`（还可能切片成
  `.0`/`.1`），但**测试与手写的 cookie 常常是 URL 编码的 JSON 明文**。
  只认 base64 会让后者全部变成「未登录」→ 401（本轮把 `paper-analysis` 从 56/56 打到 12/21）。
- **`not null` 的 jsonb 列不能写 `null`**：会撞 23502。
  症状很迷惑 —— **新建**行 500、**更新**已有行却正常（因为有旧值）。
  正确做法是「没有值时**省略这个键**」，让数据库默认值生效。
- **`upsert`（PostgREST）是整行覆盖**：payload 里没带的列会被写成 NULL。
  同一行要被多个工具共用时，这会造成**静默的数据丢失**；
  要么用合并语义（先读旧行），要么把 payload 补全。
- ⚠️ **合并语义的成败取决于「那次读旧行」是否可靠**（2026-10 实测）：
  读失败被 `softFail` 吞成空数组 → 被当成"没有旧行" → 没传的列写成 NULL。
  症状极难发现：**接口返回 `200 ok:true`，而库里的列已经被抹成 null**。
  所以：**写**路径的读失败必须**抛错、中止写入**；**读**接口才该软降级（不 500）。
  两者取舍**故意不同**，别为了"统一"把任何一边改掉。
  （本轮踩到的真实案例与防护：`StudentRowReadError` + `tests/students-unified.test.mjs` 第 2c 组）

### 5. 「先显示缓存」类的优化，测试必须钉住「仍然拉了新数据」

最危险的失效方式不是「慢」，而是**静默不再更新**（或者**静默变空**）。
`unstable_cache` 那次就是：页面不报错、只是什么都没有。
所以这类改动一定要有「**确实发了真实请求**」和「**缓存命中时数据不为空**」两条断言。

### 6. 改中间件 = 改全站鉴权入口，风险最高

- 改完必须跑 `tests/middleware-cache.test.mjs`（含「第 2 次 `user_roles` 归零」
  与「关掉开关后仍会查」两条钉子）。
- 想测「token 快过期」这类场景，用 `tests/_helpers.mjs` 的
  `sessionCookieExpiringIn()` —— 它**只改 `expires_at`**，
  `access_token`/`refresh_token` 仍是真 token，所以行为是真的、也能被计数。

### 7. 别信「本机毫秒数」

本机到 Supabase 只有约 90ms，用户环境 400–500ms。
**看调用次数，不要看毫秒**（本文件与 `perf-notes.md` 都强调过）。
耗时断言要么不做，要么留很宽的区间。

### 8. ⚠️ **绝不要用 PowerShell 的 `Get-Content` / `Set-Content` 改源码文件**（2026-10 实际踩到，代价约一小时）

本会话里我用 `Get-Content -Raw` 读、`Set-Content -NoNewline` 写，结果**把两个源文件写成非 UTF-8**：
读的时候按系统编码（GBK）解、写回去又是另一套编码，**每个多字节字符的最后一两个字节被换成 `?`**
（app.js 里 1747 处、route.ts 里 146 处），文件里散落着坏字节，读不出来也搜不全。

**正确做法**：
- 改源码**只用编辑工具**（读取/写入/替换都由工具按 UTF-8 处理）；
- 真要在命令行里批处理文本，用 **Node**：`fs.readFileSync(p, "utf8")` / `fs.writeFileSync(p, t, "utf8")`；
- **判断有没有被写坏**（一句就够，写进习惯里）：
  ```js
  const t = require("fs").readFileSync(f, "utf8");
  console.log((t.match(/\uFFFD/g) || []).length, t.includes("某个已知中文"));
  ```
- 真写坏了：`git checkout -- <文件>` 取回干净版本；
  **未提交的改动无法从磁盘还原**（编码损坏是信息丢失，不是"重新解码"能救的）——
  所以**改一会儿就提交一次**，别把一整天的工作留在工作区。

### 10. 新增「平行入口」时，必须逐条对照老入口做的事（2026-10 实际踩到）

学校卷子识别那条路（新入口）建好 `paper` 之后**漏了 4 步收尾**，而学科网那条老路
（`adoptPaperText()`）每一步都有：展开「📋 试卷信息」与「🔎 解析结果」面板（HTML 里默认
`display:none`）、更新步骤条提示、渲染逐题列表。

**现象很误导**：数据全对、控制台无报错、结果区还显示了"✅ 已生成题目结构"，
**只是屏幕上看不到那两个面板**——测试当时只断言了数据与结果文案，所以全绿。

**做法**：
- 写新入口前，先**通读老入口的整个函数**，把它的收尾步骤一条条列出来（面板显示 / 渲染调用 / 提示 / 持久化），
  再决定哪些要做、哪些刻意不做（**刻意不做的也要写注释说明原因**）；
- 两处相邻时留一句"与 XXX 保持同一套收尾步骤"的注释互相指向；
- 测试要断言**用户看得见的东西**（面板可见性、列表行数），不要只断言数据与 toast 文案。

### 11. 一个字段只能有一个「权威形态」，派生值别当权威（2026-10 实际踩到）

试卷分析里的「难度」有两个形态：**数字系数 `coeff`** 与**文字标签 `difficulty`**（还有 `grade` 档位）。
派生的那份只是给人看的。学校卷子那条路只写了文字标签、`coeff` 留空，结果
**所有按系数判断的功能静默失效**——「容易题满分·其余留空」点了一点反应都没有（用户报的最高优先级 bug）。

**做法**：
- 新增一条产生数据的路径时，**先找出这个字段的"权威形态"**（哪个被下游计算真正读取），
  再把它派生出来的展示值算出来 —— **不要反过来只写展示值**；
- 拿不准时全局搜一遍这个字段（这里是 `q.coeff` / `q.grade`），看谁在读它；
- 兜底可以加（这里 `fillAll` 用现成的 `labelToGrade` 兜了一层），但**兜底不能替代权威值**。

### 9. 桩上游返回固定内容时，测试只证明「管道通」，不证明「效果好」

AI 功能的测试里，桩上游返回的是**固定 JSON/文本**，所以断言只证明
「请求发出去了、返回被正确解析与呈现」——**不证明真实模型的识别质量**。
交付这类功能时，**必须明确告诉用户"要拿真实素材实测"**（并说清调优的旋钮在哪，
例如把图片长边从 1600 提到 2200），不要让人以为"测试全绿 = 识别准"。

### 12. 两个函数都「读整篇 → 改自己那块 → 整篇写回」时，**并行 = 互相覆盖**（2026-10 实际验过）

用户要求把两个 AI 润色入口合并成"点一次都润"（建议段 + 错因列），并特意问"哪种最不容易出问题"。
查代码发现两个函数都是 **读 `#reportText` 全文 → 只改自己那一段 → 整篇写回**：
并行跑的话，两个都先读同一份旧文本，**后写回的那个会把前者的成果整段抹掉**。

**验证方式（值得学的做法）**：不靠推理，直接把实现临时改成并行跑一遍测试 ——
断言立刻红成 `建议段是AI: false, 润色行数: 3`（建议段的成果被覆盖），
于是"必须串行"这句话就有了**实验证据**，而不是一句设计口味。

**做法**：
- 合并多个"各自整篇写回"的函数时：**默认串行**；真要多快，先把它们改成
  **各自返回片段、由调用方统一合并**（改完再谈并行）；
- 顺带把失败策略定清楚并写进测试：**失败的那一步重试一次 → 仍失败就保留另一步的成果 → 绝不整篇回滚**
  （回滚等于白花已经付钱的那次 AI 调用）；
- 会员/权限类失败**不要重试**，也别继续打下一步（省一次注定失败的调用），并在汇总里标成「未执行」，
  别让用户以为重试过了。

### 13. 「初版功能」一律配一个**后台能关掉**的开关（2026-10 起的新约定）

用户 2026-10 的要求：初版功能要能**随时撤**，而且最好在**管理后台**点一下就关（不用改代码、不用等部署）。

已落地的通用机制（`feature_flags` 表 + `/admin` 的「功能开关」+ `src/lib/feature-flags.ts`）——
**新增一个开关要动三个地方，缺一条后台就管不住**：

1. **登记**：`src/lib/feature-flags.ts` 的 `FEATURE_FLAG_REGISTRY` 加一条
   （`key` / `label` / `note` / **`param`（关闭参数名）** / `tools`（作用于哪个 slug））；
2. **迁移**：`supabase/migrations/00xx_*.sql` 里补一条**同 key 的种子**
   （表只存状态，代码才是"谁受影响"的来源）；
3. **工具页认这个参数**：例如 `companyExportDisabled()` 读 `?nocompanyexport=1`。
   参数由 **`ToolPageShell` 服务端拼到 iframe 的 src 上** ⇒ **工具页代码一行都不用改**
   （这条是关键：别让每个工具自己去查库、更不能每个功能一套关法）。

两条口径：
- **读不到开关表时一律当"开启"**（DB 抖一下不该悄悄把功能干掉），后台要显示"表还没建 + 要跑哪个迁移"；
- **优先级：URL 参数（含后台拼的）> 代码常量** —— 后台关掉＝一定关。

⚠️ 坑（实测）：PostgREST 对"表不存在"返回的是 **`PGRST205`**，不是 Postgres 的 `42P01`；
只判 `42P01` 会让"该跑哪个迁移"的提示根本不出现。判"表在不在"要两者 + 消息关键词一起判。

## 开工前先确认的路径与命令（省得第一步就卡住）

|---|---|

| git | `D:\my-website\.tools\git\cmd\git.exe`（**不在 PATH**，要用全路径调用） |

| 浏览器自动化 | 用 CDP + 无头 Edge；`tests/_helpers.mjs` 已有现成的登录/导航/求值工具，**别重写** |

> 再怀疑代码。** 一次只跑一个 runner。

- 在 Vercel 看 Deployments 状态

- 在网站 `/admin` 开会员

用户不能做：
- 读代码、改代码
- 分析日志、定位 bug

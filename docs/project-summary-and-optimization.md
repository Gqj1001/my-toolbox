# 项目阶段性总结与优化报告

> 2026-10-24 · 面向非技术负责人，也作为后续开发的底稿。
> 统计口径：仓库 `D:\my-website\my-toolbox`；代码行数含 `src / public/tools / tests / supabase / scripts`
> （不含 `node_modules`、`.next`、`.git`、文档与图片）。测试数为本轮实测（若未特别说明，均为串行全套）。

---

## 一、整体架构现状

### 1. 规模（粗算）

| 范围 | 文件数 | 行数（约） | 说明 |
|---|---:|---:|---|
| `src/`（Next 页面 / API / 组件 / lib） | — | **19,100** | 服务端页面、API 路由、学情/档案/后台逻辑 |
| `public/tools/`（工具页） | — | **21,300** | 反馈 / 数学方案 / 试卷分析 / 全学科 v2 / 方案生成器等静态工具（含少量 vendor） |
| `tests/` | — | **21,000** | 纯函数 + 真 HTTP + 无头 Edge 端到端 |
| `supabase/` | — | **5,400** | 迁移与 SQL 自检 |
| `scripts/` | — | **3,000** | 推送、构建辅助、运维脚本 |
| **合计** | **277** | **约 69,700** | 不含文档；`public/tools` 的 vendor 会随版本变化 |

> 这个规模已经不是“小脚本”，而是**一个有 10+ 个工具、带权限/会员/档案/AI/导出/测试的完整业务系统**。
> 继续加功能时，边界和“唯一来源”比代码量更重要。

### 2. 技术栈

- **框架**：Next.js **16.3.8**（App Router、Server Components、Route Handlers、Server Actions）、React **19.2.8**；
- **数据库/鉴权**：Supabase（Postgres + Auth + RLS + PostgREST RPC）；
- **部署**：Vercel（Next 服务、Edge/Node 中间件、静态工具页）；
- **样式**：Tailwind CSS 4；
- **图表**：Chart.js 4.6.1（学情折线/环形/雷达；后台大盘饼图/折线）；
- **文档导出**：公司 docx 模板引擎 + 自研 docx 组装（JSZip 风格，无第三方 Office 依赖）；
- **AI**：DeepSeek（`deepseek-flash` 默认，`AI_KEY` 只在服务端）、可切换视觉模型；
- **测试**：Node 原生脚本 + CDP 无头 Edge + 本地 `next start` + 测试桩上游；
- **工具页形态**：`public/tools/*.html` 静态页面，通过 `ToolPageShell` 的 iframe 挂载；核心逻辑部分抽到 `js/core/` 供老/新工具共用。

### 3. 分层

```
浏览器
 ├─ Next 页面（/tools, /dashboard, /admin, /account）
 │   ├─ Server Component：读 viewer / 档案 / 统计
 │   ├─ Client Component：AI 报告面板、图表、后台交互
 │   └─ API Route：AI 代理、文件解析、视觉识别、档案 CRUD
 ├─ iframe 工具页（public/tools/*.html + js/core）
 └─ Supabase（Auth + Postgres + RLS + SECURITY DEFINER RPC）
```

**关键设计（值得保留）**：
- 写档案只有一条路：`/api/students` / `feedback-db.upsertStudent`，服务端按键合并 `extra`；
- 读统计只有一条路：`src/lib/student-report.ts`（页面与 AI 摘要同源）；
- AI Key 只在服务端；上游错误不透传；AI 输出有行数/键数契约；
- 公司模板导出不改现有生成逻辑，只做“以模板为底、按标签替换”；
- 管理员跨用户读取走 SECURITY DEFINER 函数（0026/0027/0028），不放宽老师端 RLS。

### 4. 测试覆盖度

- **55 套 / 1811 项断言**（本轮全部为**串行**跑；含 1 套外部 `verify-checklist`）；
- 覆盖形态：
  - 纯函数（解析/算分/分摊/报告/权限缓存/Markdown 表格）；
  - 真 HTTP（鉴权、错误码、幂等、RLS 隔离）；
  - 无头 Edge 端到端（后台、档案、导出、AI 面板、筛选/下钻）；
  - 静态契约（迁移、提示词、关键源码约定）；
  - 少量**变异自证**（把 bug 装回去必须红）。
- ⚠️ 这不是“行覆盖率”。没有 Istanbul/c8 的行覆盖数字；**不要对外说“覆盖率 90%”**。
- 测试依赖**真实 Supabase 项目 + 本地 3000 + 无头 Edge**；全套约 1 小时，且必须串行（并行会假红）。

## 二、技术债与隐患

按“会不会咬人”排序。

### 1. 权限/RLS：最需要收口

- 普通表（`feedback_students` / `feedback_history`）是 **owner-only RLS**；
- 后台跨用户读取靠 `0026` / `0027` / `0028` 的 SECURITY DEFINER 函数；
- 目前**没有** `campus_id` / `region_id` 列，A2 的“校区”是按**创建老师当前资料**推断的；
- 风险：
  - 新加一个后台查询，如果直接 `.from("feedback_students")`，会**静默只看到管理员自己**（和“后台资料未填”同一类 bug）；
  - 老师调校区会改变历史归属（A2 用 `extra.institutionCampus` 手动纠正来兜底）；
  - `role='admin'` 目前没有“超级/大区/校区”的区分，所有 admin 等价；
  - 现有 `admin_list_users()` 与三个档案 RPC 各自校验 `is_admin()`，继续加 RPC 会重复。

### 2. 指标口径：有些是“估算”，不是真实考勤

- 学生表**没有 `created_at`**（只有 `updated_at`），所以“本月新增”按“最早一条历史记录”推断；
- 没有“每次课消耗几课时/是否出勤”的数据，后台“本月消耗课时”按**本月课后反馈条数 × 2 课时估算**；
- “进行中方案”按“近 90 天有 math-plan 记录”定义，不是真正的“未结课”；
- 风险：老板拿大盘数字对外汇报时，会把**估算**当**精确值**。
  **页面已标“约/按…估算”，后续应补真实考勤/课时流水。**

### 3. 工具页体积与重复逻辑

- `feedback.html`、`math-plan.html`、`paper-analysis/js/app.js` 都是**大文件**（单文件几千行）；
- 老数学版与新全学科 v2 共享 `js/core`，但 UI 层仍有各自一套渲染/导出流程；
- 风险：改一处解析规则，两套 UI 的边界容易漏；纯函数测试能兜住 core，但 UI 行为仍靠端到端。

### 4. `extra` JSON 键约定没有版本化

- 现在 `extra` 里至少有：`cls`、`book`、`exam`、`phase`、`score`、`target`、`targetScore`、`totalHours`、`institutionCampus`…
- 服务端做按键合并（`mergeExtra`），不会互相覆盖；但**没有 schema/版本号**；
- 风险：以后改键名（如 `targetScore` → `goalScore`）要同时改多个工具与报告，老数据没有迁移标记。

### 5. 迁移与部署流程靠人工

- 迁移文件在 `supabase/migrations/`，但**没有自动 runner**；0021–0028 都是人工在 SQL Editor 执行；
- 风险：新环境/新同事漏跑一条，页面会“看起来正常但功能静默缺失”；测试也会因缺函数红/跳过；
- 目前靠“页面提示迁移文件名 + 测试断言”兜底，但不是强保证。

### 6. 缓存与并发

- 角色/会员：中间件 `roleCache` + 页面侧 `userRolesCache` 两层 30 秒 TTL；
- 档案/历史/资料：25 秒进程内缓存，写后主动清；
- 已修“查询失败被当无角色缓存”的 Bug，但**两层缓存 + 多实例**仍可能让角色/封禁最多延迟 30 秒；
- 风险：管理员改角色后，另一个实例上的老师可能短时间内仍按旧权限；封禁同理（已和用户确认接受）。

### 7. AI 报告与提示词

- 提示词分散在 5+ 个路由/文件（学情、补录、方案生成、试卷归因、反馈润色）；
- 模型名/Token 上限/超时在多处重复默认值；
- 报告是**一次性文本落库**，没有“结构化字段版本”，Markdown 表格靠前端解析；
- 风险：改一个提示词可能只改了一处；不同工具的 AI 行为口径逐渐漂移。

### 8. 后台大盘的规模上限

- 下拉选项取前 1000 份、表格当前页 500 份；统计函数每次实时聚合全表；
- 目前机构规模小没问题；到几千/几万学生时，`admin_archive_stats()` 的全表扫描 + 多子查询会变慢；
- 风险：大盘打开变慢、Vercel 函数超时。

### 9. 测试/CI 成本

- 55 套串行约 1 小时；依赖真实 Supabase、3000 端口、无头 Edge；
- 没有 CI（GitHub Actions/Vercel 构建只跑 `next build`，不跑全套）；
- 风险：合并前靠人工跑；跨会话容易忘；时序类断言偶发（已用轮询缓解）。

### 10. 安全/隐私

- AI Key 只在服务端，未泄漏（测试有断言）；
- 但学生姓名、反馈正文、成绩都在 Supabase；目前没有“数据保留期限/导出后删除”的产品化策略；
- `.test-users.json` 含测试账号密码（仅本地，不提交；仍建议改成环境变量）；
- 管理员可跨校区看全部（A2 是老板一人），后续分级前要明确“谁看谁”的审计。

## 三、未来 1–3 个月功能建议（产品视角）

### P0：把“估算”变成“真实数据”（1–2 周）

1. **课时流水/考勤**：每次课后反馈可填“本次消耗课时”（默认 2，可改），后台按流水汇总；
   - 解决“本月消耗课时”估算；
   - 为“课耗/续费预警”打基础。
2. **学生 `created_at` + 方案状态**：补真实建档时间、方案“进行中/已结课”状态；
   - 大盘“本月新增/进行中方案”变精确。
3. **归档/删除策略**：毕业/退费学生归档，不参与大盘；保留历史可查。

### P1：老师效率（2–4 周）

1. **档案时间轴**：把方案 / 试卷 / 反馈 / 学情报告按时间轴串起来，一眼看“这个学生这学期发生了什么”；
2. **报告模板**：同一份统计一键生成“家长版 / 机构会议版 / 教师版”，Markdown 表格可配置；
3. **一键周报/月报**：按老师/校区批量生成，减少重复写；
4. **错题本/题库**：试卷分析的错题沉淀成学生错题本，支持按知识点复习；
5. **批量补录/导入**：Excel/Word 批量导入历史档案，减少“一条条补”。

### P1：管理与权限（2–3 周）

1. **三级权限（Owner / 大区 / 校区）**：按 `docs/three-level-permissions-plan.md` 分阶段落地；
2. **校区/大区维度**：`campuses.region_id`、学生归属快照，支持按大区/校区看大盘；
3. **操作审计**：谁改了档案、谁看了哪个校区，至少记录管理员操作。

### P2：增长与交付（1–3 个月）

1. **家长端只读分享**：生成带有效期的分享链接/PDF，不暴露账号；
2. **移动端适配**：老师课后在手机上填反馈/看档案；
3. **会员/校区计费**：按校区/坐席/用量计费，后台看 AI 成本；
4. **数据沉淀**：机构级“提分案例库”“知识点薄弱排行”，反哺教研；
5. **通知**：课消不足、目标未达成、长期未反馈提醒。

> 建议顺序：**先真实课耗/建档时间 → 再时间轴/报告模板 → 再权限分级 → 最后增长功能**。
> 权限分级不要和“课耗改造”同时上，否则 RLS 与数据口径一起变，回归范围太大。

## 四、性能与成本优化建议

### 1. 数据库 / 查询

- 给高频过滤加索引（需确认现有索引后补）：
  - `feedback_history (user_id, student_name, created_at desc)`；
  - `feedback_history (tool, created_at desc)`；
  - `feedback_students (user_id, updated_at desc)`；
  - `user_profiles (campus)`。
- 大盘统计改为**每日汇总表/物化视图**（`archive_stats_daily`），页面只读汇总；避免每次全表扫描；
- 后台列表改为**服务端分页**（page/pageSize），不要一次取 1000 行做下拉；
- 大区/校区分级后，RLS 策略里避免每行调用复杂函数，用 `security definer` 的“范围 ID”先算一次。

### 2. 前端

- `chart.js` 目前直接 import；可改成 `next/dynamic` 懒加载，只有打开学情/大盘才下载；
- 大盘饼图/折线图只在有数据时渲染（已做），避免空图表；
- 工具页大 HTML 可按“首屏/导出/识别”拆模块，减少首屏解析；
- 图片识别仍限制 4MB / 20 页；pdf.js 已懒加载，保持。

### 3. AI 成本

- 报告/归因/目标生成都有 `max_tokens` 上限；继续按任务给预算，不要一刀切 6000；
- 同一份统计重复生成时，前端提示“已生成过，是否重新生成”（已有部分确认）；
- 长材料先本地抽取/截断，再喂模型；避免整份 PDF 原文进上下文；
- 记录每次 AI 调用的 token/费用（服务端日志），后台出“本月 AI 成本”；
- 非会员/无 Key 的请求在调用前拦截（已有）。

### 4. 部署/运行时

- Vercel 函数区域尽量靠近 Supabase 区域，减少跨区往返；
- 中间件只做鉴权/角色，不查业务表；业务查询放页面/Route；
- 静态工具页走 CDN，不要经过 Node 函数；
- 生产不要开 `ALLOW_DEBUG_CACHE_CLEAR` / `DEBUG_CACHE_TOKEN`（已有约定）；
- 监控：Vercel 函数耗时、Supabase 慢查询、AI 502/超时率；大盘慢查询优先看 `admin_archive_stats`。

### 5. 测试成本

- 纯函数套件（约 20 套）可在 CI 每次跑；真服务/浏览器套件按 PR 或每日跑；
- 把“需要 3000 端口”的套件统一到一个串行 runner（已有 `.tmp-planning-samples` 脚本，但未进仓库）；
- 长期可把 Supabase 测试项目独立出来，避免测试数据与线上混用。

## 五、一句话结论

**底座已经够稳（写路径唯一、统计同源、AI 护栏齐全、55 套回归），下一阶段最大的价值不是再加一个工具，而是：**
1. 把“课耗/建档/方案状态”变成真实数据；
2. 把权限从“所有 admin 等价”升级为“Owner / 大区 / 校区”（先方案后代码）；
3. 把后台大盘从“实时全表聚合”升级为“每日汇总 + 服务端分页”。

> 本报告只做总结与建议，**没有改任何代码/表**；三级权限方案见 `docs/three-level-permissions-plan.md`。

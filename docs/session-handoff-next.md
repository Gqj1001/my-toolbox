## 5. 关于「工作区文件太多太乱」——要不要整理？

**结论：现在不需要整理，也不会影响功能。**

理由（按重要性）：

1. **乱的是"开发期中间物"，不是运行代码。**
   真正上线的东西都在 `public/tools/`（工具页）、`src/`（服务端与页面）、`supabase/migrations/`（建表脚本）里，
   结构是清楚的：一个工具一个目录。
2. **最"吵"的 `.tmp-planning-samples/` 是我不进 git 的临时目录**（分析脚本、导出样本、日志、变异备份）。
   ⚠️ 更正一句：它**没有**写进 `.gitignore`（我核过 `git check-ignore` 不认它），
   所以 `git status` 里会一直挂着一个 `?? .tmp-planning-samples/` —— **但它从来没被提交过**
   （每次 `git add` 都是点名文件，从没用过 `-A`）。对网站零影响，删掉只是下次我得重写分析脚本。
   **要清爽的话，最省事的动作就是：把它加进 `.gitignore`，或者直接删掉。**
3. **测试文件多（40+ 个）是资产，不是垃圾。** 那是"改动不会悄悄弄坏别的功能"的唯一保证。
   这个项目历史上踩过很多坑（日期静默变空、模块名被切、并行跑假红…），每一条都对应一个测试。
4. **`docs/` 里有 20 多份文档**，但它们是**按用途分的**：总览、待办、工作指南、每个工具一份、
   每件专题一份。真要整理，最多是"给 docs 加一个索引"，而不是删。

**如果以后真的想收拾，我建议这样做（按收益排序，都不急）：**

| 动作 | 收益 | 风险 |
|---|---|---|
| 清 `.tmp-planning-samples/`（或只留日志） | 看着清爽 | 低（下次要重写分析脚本，约 10 分钟） |
| 把 `docs/` 里"已完成的一次性方案"移到 `docs/archive/` | 找文档快一点 | 低（只要不改链接） |
| 给测试文件加个 `tests/README.md` 说清"哪套管哪块" | 后人接手快 | 低 |
| ❌ 把 `docs/` 合并成一个大文件 | 反而难查 | 高 |

**一句话**：**功能不受影响，不用现在动。** 真想清爽，最省事的是删 `.tmp-planning-samples/`。

## 6. 这次会话我踩到并记下的坑（省得下次重踩）

1. **改"输出口径"时，要顺着数据流往上找"有没有别处按旧口径估过账"**。
   课时从小数改整数时，选模块的预算估算（`weightOf`）也必须跟着改，否则会"选进一堆模块却只给得起 1 课时"。
2. **新分支别放在"前置校验"之后**。`setDate` 第一版写在「缺学生姓名 → 400」后面，
   而它按记录 id 定位、不带 name ⇒ 每次都被顶回去。
3. **同一份测试给某行加了按钮，别的测试用 `querySelector('button')` 就会误判**。
   `archive-students` 因此红了 3 条 —— 改成按**文案**找按钮。
4. **PowerShell 里嵌 Node 单行脚本，引号会被吃掉**。复杂脚本要落成 `.cjs` 文件再跑（这一批踩了 4 次）。
5. **变异测试的锚点要用正则/先看清实际格式**，别凭记忆写：我两次把 `name: "Unit 1"` 的引号数错，一条都没改到。
6. **测试中途抛错会跳过收尾清理**，脏数据会污染下一次跑（`__合并语义探针` 就是这么攒下来的）。
   改测试时注意别让断言在"清理"之前抛。

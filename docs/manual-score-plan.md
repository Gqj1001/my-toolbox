# 学员档案 · 手动补录成绩（**已实现**，2026-10 第十四批）

> 来源：用户 2026-10 的需求原话 ——
> 「这个是否可以在学生档案里增加一个自己填写的功能，有时候我们不在这里考试，在其他地方的考试
> 也具备一定参考意义，我们可以做数据的收集，然后在这个功能中填写，最后 AI 分析学期的时候
> 依旧会把这个考虑在内」。
>
> 用户拍板：① 数据复用档案记录（`tool='manual'`）；② 这轮就做到"能填 + 能看见 + 自动进趋势与 AI"；
> ③ 支持**删除**（填错了重录），不做行内编辑。**本文是方案 + 实现记录。**

## 0. 一句话

学员档案详情页多了一个 **「📝 补录一次成绩」** 表单（考试名 / 日期 / 得分 / **满分** / 类型 / 备注）→
写进去就是一条普通的 `feedback_history` 记录（`tool='manual'`）⇒ **记录列表、学情分析的
「成绩趋势」与 AI 报告全部自动把它算进去**（趋势那一段本来就扫全部带分数的记录，不挑工具）。

## 1. 为什么复用档案记录、而不是新开一张表

| 选项 | 结论 |
|---|---|
| **复用 `feedback_history`（已选）** | 记录列表、趋势、AI 报告**全都自动接上**；只加一条约束 + 一个白名单 |
| 新开 `manual_scores` 表 | 学情分析**不会自动看到**它 ⇒ 要另写一套聚合，而且**同一件事两个来源**（本项目的老坑） |
| 塞进学生档案的 `extra` jsonb | `extra` 是"学生是谁"的身份字段，塞成绩会让"换个学生"的污染风险变大，也进不了趋势 |

成绩的**权威形态**就是 `(score, full_score, date, title)` 四件套 —— 与试卷分析写的那条**完全同构**，
所以补录的成绩与自动存的成绩在报表里**长得一模一样**（这正是想要的）。

## 3. 表单字段与口径

| 字段 | 必填 | 口径 |
|---|---|---|
| 考试名称 | ✅ | 如「学校期中考试」 |
| 考试日期 | ✅ | 默认今天（用**本地**日期，不用 `toISOString()`——那是 UTC，晚上会差一天） |
| 得分 | ✅ | 数字 |
| **满分** | ✅ | 默认 150。**必须填**：没有满分就算不出得分率，`student-report.ts` 会把这种记录排除在趋势外（老师会觉得"填了没用"） |
| 考试类型 | ⬜ | 校考 / 月考 / 期中 / 期末 / 模考 / 其他（留空 = 不写空串，存 null） |
| 备注 | ⬜ | 最多 500 字，进记录正文 |

正文固定写成 `手动补录 · 由老师在档案页填写` + 逐行字段，**列表里一眼看出这条不是工具生成的**。

三条硬规则（纯函数里钉住）：**0 ≤ 得分 ≤ 满分 ≤ 1000**；日期走**真日历校验**（`2026-02-30` 一律拒）；
长度上限（姓名 100 / 名称 100 / 备注 500）。

## 4. 要用户做的一件事（以及不做会怎样）

在 **Supabase → SQL Editor** 里整段执行：

```
supabase/migrations/0019_history_tool_allow_manual.sql
```

- **不做也安全**：档案页、记录列表、学情分析统计、三个工具**全都照常**；
  只有点「保存这条成绩」那一下会失败 → 接口返回 **409** 并**点名这个文件**，页面照着提示做即可。
- 幂等，可重复执行；只动那一条 CHECK。
- 跑完之后 `tests/manual-score.test.mjs` 会**自动从"A 分支"切到"B 分支"**
  （真测保存 → 读回 → 进趋势 → 删除整条链路），无需改测试。

## 6. 本轮不做（记在这里）

- 从**外部机构的报告截图**里自动识别成绩（属新 AI 功能，另开）；
- 排名（表里没有这一列，补录只收集分数与满分）；
- 行内编辑（只有"删除后重录"，用户已拍板）；
- 全学科下拉的完整适配（`subject` 字段先留口子、默认数学）。

## 7. 实做记录：这一轮**测试当场抓到的真 bug**（值得留着）

新套件第一次跑就红了 2 条，全是真 bug，不是测试写错：

**症状**：迁移没跑时，本该返回 **409 + 点名迁移文件**，实际返回 **500 +「保存失败，请稍后重试。」**
—— 老师照着页面提示完全无法定位（而旧提示里点名的还是 `0016`，跑了也没用）。

**根因两条**：
1. 判"是不是撞了 `feedback_history_tool_check`"**只看了 `error.message`**；
   而 PostgREST 把约束名放在 **`details`** 里，`message` 只有
   `new row for relation "feedback_history" violates check constraint …`。
2. 迁移文件名**写死在路由里**（`0016`），0017/0019 之后就成了错误指引。

**修法**：判定改成拼 `code | message | details | hint` 一起判；
迁移文件名收拢到 `src/lib/manual-score.ts` 的 `TOOL_CONSTRAINT_MIGRATION`（唯一来源），
并用契约测试钉住"它必须等于仓库里**最后一条**定义这条 CHECK 的迁移"。

> 这条正是 `docs/dsh-work-guide.md` 坑 9（"桩上游只证明管道通"）的同类：
> **错误分支从来没被真跑到过**。现在两个写历史的接口共用同一份判定，且有 5 条断言守着。

## 8. 变异自证（用户规矩：真 bug 必须证明"退回去就一定红"）

三条，全部**实做**过（不是声称）：

| # | 把什么退回去 | 结果 | 说明 |
|---|---|---|---|
| **M1** | `SOURCE_TOOLS` 去掉 `'manual'` | `student-report` **43/45**，红的正是<br>「进记录概览的按工具统计」与「manual 已登记为一种来源」 | ✅ 断言真的会红，其它 43 条不受影响 |
| **M2** | `isToolConstraintError` 不看 `details`/`hint` | `manual-score` **31/32**，红的正是<br>「约束名只在 details 里也必须认」 | ✅ 第一次跑**没红**（断言写太松：样本里带了 `23514`），把样本里的 SQLSTATE 去掉后才真红 —— 这一步顺带发现了 M3 |
| **M3** | 判定里保留按 SQLSTATE `23514` 兜底 | —— 不是变异，是 **M2 逼出来的真 bug**：<br>`23514` = "违反任意 CHECK"，而 `feedback_students_extra_is_object`（extra 必须是 JSON 对象）**也是 23514**，会被误报成「请去跑 0019 迁移」 | ✅ 已把 `23514` 从判定里**删掉**，并加了一条"别的 CHECK 不许被误判"的断言 |

> ⚠️ **M2 的教训值得记住**：变异测试跑出"全绿"时，**先怀疑断言写松了**，而不是"这句代码无所谓"。
> 本轮如果只看第一次 M2 的结果就收工，会留下两条假绿断言 + 一个真实的误报隐患。
